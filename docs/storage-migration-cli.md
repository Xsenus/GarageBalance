# Перенос и проверка резервных копий

`GarageBalance.StorageTool` запускается оператором с конфигурацией приложения: `appsettings.json` рядом с DLL и переменные окружения. Строка подключения — `ConnectionStrings__DefaultConnection`; значения секретов и исключения провайдеров не выводятся. Инструмент не применяет миграции схемы, не переключает режим рабочего сервера и **никогда не выполняет удаление исходных архивов**.

Работайте в закрытом каталоге вне Git. На Linux JSON создаётся с правами только владельца; на Windows заранее ограничьте ACL каталога учётной записью оператора. Контрольная точка содержит имена, размеры и хеши архивов, но не секреты подключения. Отчёт `report` дополнительно содержит реальные относительные адреса копий для восстановления каталога; его нельзя публиковать.

## Команды

| Команда | Назначение |
|---|---|
| `inventory` | Проверяет все локальные управляемые архивы: имя, размер, SHA-256, `pg_restore --list`, имеющийся manifest. Валидный старый архив без manifest показывается пригодным к регистрации. Ничего не записывает. |
| `plan` | Для каждого локального архива показывает регистрацию, продолжение доставки, сохранение tombstone или блокирующий конфликт. |
| `diff` | Показывает новые локальные архивы, отсутствующие локальные копии, конфликты, tombstone и очередь защиты. |
| `copy` | Создаёт новый фиксированный снимок миграции, регистрирует валидные архивы, атомарно добавляет отсутствующие manifest и обрабатывает доставку только объектов снимка. |
| `resume` | Продолжает именно прежний снимок с сохранённого индекса; новые архивы не захватывает. Проверяет неизменность конфигурации, исходников и поколений. |
| `delta-sync` | Расширяет прежний снимок новыми локальными и зарегистрированными объектами. Tombstone сохраняет, изменённые исходники не перезаписывает. |
| `verify` | Читает полные байты каждой пригодной копии и сравнивает SHA-256; с `--execute` обновляет дату подтверждённой проверки. Не назначает ремонт. |
| `repair` | Та же проверка; с `--execute` назначает ремонт повреждённых/отсутствующих копий и выполняет ограниченное число задач доставки. Повторно проверяет результат. |
| `status` | Компактные количества по состояниям каталога; при `--checkpoint` — сохранённое состояние миграции. |
| `report` | Полный инвентаризационный отчёт с каталогом текущих поколений и относительными адресами копий. Не заменяет зашифрованный recovery bundle. |
| `cutover-check` | Проверяет физическую доступность и SHA всех требуемых независимых и off-site копий каждого сохранённого архива. Пустой каталог, неучтённые архивы или неполное покрытие блокируют переключение. |
| `rollback-check` | Требует проверенный файл каждого сохранённого объекта в прежнем локальном каталоге под прежним плоским именем. B-only архив не считается готовым к откату; оставшийся локально tombstone блокирует откат старого бинарника, чтобы удалённое не появилось снова. |
| `resume-reconciliation` | После расследования снимает сохранённую защитную паузу массового ремонта; требует `--execute --reason "Причина решения оператора"`. Без `--execute` только показывает состояние. |

Изменяющие команды без `--execute` работают как dry-run: без manifest, контрольной точки, задач и изменения БД. У `verify` dry-run всё же читает реальные байты, но не сохраняет даты. `copy --execute`, `resume`, `delta-sync` требуют `--checkpoint <path.json>`. Существующая контрольная точка не перезаписывается командой `copy`: используйте `resume`, `delta-sync` или новое имя после проверки плана.

В режиме `Single` команда `copy` регистрирует проверенные локальные архивы без удалённых задач. После включения `AsyncMirror` выполните новый просмотренный план с новой контрольной точкой: изменение режима/политики намеренно не проходит незаметно через старый `resume`.

## Порядок запуска

Пример после применения штатных миграций БД и настройки независимых назначений:

```powershell
dotnet run --project backend/GarageBalance.StorageTool -- inventory --output D:/PrivateStorage/inventory.json
dotnet run --project backend/GarageBalance.StorageTool -- plan
dotnet run --project backend/GarageBalance.StorageTool -- copy --execute --checkpoint D:/PrivateStorage/migration.json --max-jobs 100
dotnet run --project backend/GarageBalance.StorageTool -- resume --execute --checkpoint D:/PrivateStorage/migration.json
dotnet run --project backend/GarageBalance.StorageTool -- delta-sync --execute --checkpoint D:/PrivateStorage/migration.json
dotnet run --project backend/GarageBalance.StorageTool -- verify --execute --output D:/PrivateStorage/verify.json
dotnet run --project backend/GarageBalance.StorageTool -- cutover-check --output D:/PrivateStorage/cutover.json
dotnet run --project backend/GarageBalance.StorageTool -- rollback-check --output D:/PrivateStorage/rollback.json
```

Короткий порядок: `inventory` → `plan` → `copy` → `verify`, затем delta и повторная проверка перед любым переключением. `pending` в контрольной точке означает сохранённую задолженность доставки, а не успех защиты. `copied_requires_verification` означает только завершение записи; полноценное покрытие подтверждает отдельный `cutover-check`.

`--page-size` (1–1000, по умолчанию 200) регулирует страницу чтения каталога, **не ограничивает общее число проверяемых объектов**. `--max-jobs` (1–10000, по умолчанию 100) ограничивает один запуск доставки. Для metadata установлен предел 20000 объектов/файлов: при превышении проверка завершается ошибкой, а не выдаёт ложный успешный частичный отчёт. Файлы читаются потоково; каждая проверка провайдера ограничена `OperationDeadlineSeconds`, TOC — двумя минутами.

## Сбои, безопасность и откат

Контрольная точка пишется через временный файл, flush и atomic rename, содержит версию формата и SHA-256 содержимого. Lock-файл исключает два одновременно запущенных процесса с одной точкой и остаётся рядом после завершения: это рабочий файл блокировки, его нельзя удалять во время эксплуатации (на Unix стабильный inode нужен для взаимного исключения). Общий PostgreSQL advisory lock исключает пересечение backfill с созданием/retention приложения. После аварии повторная регистрация идемпотентна; незавершённая доставка остаётся в durable jobs. Изменение политики, адресов хранилища или исходных байтов требует нового просмотренного плана, а не скрытого продолжения.

Команды доставки получают только `Replicate`/`Repair` для объектов своего снимка: накопленные `Delete` и объекты другой миграции не захватываются. Снятие логического объекта не отменяется: при повторном чтении tombstone не регистрируется и не восстанавливается.

Оба gate повторно сверяют каталог и локальный inventory после чтения копий. При конкурентном изменении данных результат блокирующий: повторите проверку в согласованное окно без новых backup/delete операций. Успешный gate не выдаёт бессрочное разрешение на будущий cutover: решение принимает оператор по свежему отчёту и успешному изолированному восстановлению. Никогда не отключайте маршрутизатор при B-only данных: сначала верните проверенные файлы локально контролируемым восстановлением и повторите `rollback-check`.

Если при `repair` обнаружено более десяти одновременно повреждённых/пропавших ранее доступных копий, инструмент сохраняет защитную паузу и не назначает ни одного ремонта в этом проходе. Обычная задолженность ещё не выполненной доставки не считается массовой порчей. `status`/`report` показывают паузу; после проверки причин оператор использует `resume-reconciliation`. Недоступная/испорченная запись защитного состояния блокирует ремонт до восстановления контроля.

Коды завершения: `0` — команда выполнена (смотрите также `dryRun`/checkpoint state); `2` — неверные параметры, небезопасный checkpoint/конфликт; `4` — нет строки подключения; `5` — некорректная storage-конфигурация; `6` — внешняя ошибка без утечки подробностей; `10` — проверка/покрытие заблокировано; `130` — отмена. Не запускайте переключение после ненулевого кода.

Старые файлы с неверным TOC, hash или manifest остаются на месте и попадают в отчёт. Их ручной разбор/карантин — отдельная операция; CLI не удаляет их и не маскирует успешной регистрацией.
