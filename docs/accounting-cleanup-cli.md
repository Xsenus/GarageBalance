# Выборочная очистка архивных гаражей

Команды обслуживания предназначены для администратора узла. Они не создают HTTP endpoint и не доступны через обычные формы. Приложение остаётся пригодным для локальной установки и VPS: служба или порт задаются явно, параметры PostgreSQL берутся из `ConnectionStrings__DefaultConnection` без вывода секрета.

## Граница удаления

Удаляются только выбранные **архивные** гаражи без:

- начального остатка или начальной просрочки;
- финансовых операций и начислений, включая отменённые;
- исправлений начального остатка;
- показаний приборов, включая отменённые;
- индивидуальных тарифных назначений, включая архивные;
- связей со сборами и списками гаражей тарифных услуг.

Предпросмотр показывает причины отказа, их общие количества и не более 100 защищённых строк. В одном плане не более 500 подходящих гаражей; default — 100. При `hasMoreEligible: true` после выполнения создаётся **новый** план следующей части. Нет операции «удалить всё», действующие гаражи не выбираются.

Приборы/подключения без показаний, периоды численности и ссылки быстрых отчётов выбранных гаражей удаляются вместе с карточкой. Владельцы, остальные гаражи, сами быстрые списки, финансовые записи, прежний аудит и provenance импорта сохраняются. Непроверенная новая связь в PostgreSQL блокирует команду, даже если для неё указан `ON DELETE CASCADE`.

## Предпросмотр

Запускать установленный `GarageBalance.StorageTool.dll` с конфигурацией нужной среды. Для VPS example:

```sh
dotnet GarageBalance.StorageTool.dll archived-garages-plan \
  --expected-database garagebalance_staging \
  --max-garages 100 \
  --output /var/lib/garagebalance-staging/private-maintenance/archive-plan.json
```

Файл должен быть новым, иметь абсолютный путь и расширение `.json`. Команда не перезаписывает существующий файл/backup manifest и не использует symlinks/reparse points. На Unix файл создаётся с правами `0600`, на Windows ACL ограничивается текущим пользователем, Administrators и SYSTEM. Храните его в private каталоге вне Git. Stdout содержит только общие количества, ID плана и отпечаток; подробные строки остаются в файле. Команда `archived-garages-cleanup` без `--execute` также выполняет только предпросмотр и требует `--output`.

Проверьте `source`: точные host/port/database, идентификатор базы/запуска PostgreSQL, узел выполнения и отпечаток схемы. Предпросмотр действует 24 часа. План не должен переноситься на другую базу, другой узел или через перезапуск PostgreSQL.

## Проверенная резервная копия

Перед удалением остановить обслуживаемое приложение. На Linux проверить именно нужную systemd-службу; для установки без службы остановить backend и использовать его точный порт. Команда требует привилегии root на Linux либо Administrator на Windows, свидетельство остановки и отсутствие других клиентских подключений к той же базе. Она не останавливает чужие процессы и не завершает подключения автоматически.

Получить свежий согласованный `pg_dump --format=custom --no-owner --no-acl` точной базы и сохранить файл private. Восстановить его на установленном PostgreSQL только в отдельную тестовую базу, не поверх рабочей/production/чужой базы. До восстановления проверить имя, назначение, host/port и подключения. Не запускать приложение, фоновые задания, интеграции, печать или уведомления на восстановленной копии. Проверить успешность восстановления и соответствие структуры/миграций, затем удалить task-owned проверочную базу и файлы по согласованному inventory.

Private receipt формата 1 готовится **после реальной успешной проверки восстановления**. Сам verifier не выполняет restore drill; он проверяет предоставленное администратором доказательство, источник/схему, срок, custom header и фактический SHA-256 файла. Не ставить `restoreSucceeded: true` по факту существования файла.

```json
{
  "formatVersion": 1,
  "source": {
    "executionHost": "узел из плана",
    "databaseHost": "host из плана",
    "databasePort": 5432,
    "databaseName": "точное имя из плана",
    "databaseIdentifier": "идентификатор из плана",
    "schemaFingerprint": "отпечаток из плана"
  },
  "backupPath": "/absolute/private/source.pgdump",
  "sha256": "64 шестнадцатеричных символа фактического SHA-256 файла",
  "backupCreatedAtUtc": "время завершения согласованной копии в UTC",
  "restoreVerifiedAtUtc": "время успешной проверки восстановленной копии в UTC",
  "restoredSchemaFingerprint": "проверенный отпечаток схемы восстановленной копии",
  "restoreSucceeded": true
}
```

Этот JSON иллюстрирует структуру; строки-заглушки надо заменить, а `source` — скопировать целиком. Копия не старше 24 часов, проверка не раньше копии, будущие даты запрещены. Dump до новой миграции не подходит для удаления после неё: нужны новая копия и новая проверка схемы. Connection strings, пароли, raw dump и private receipts не добавлять в Git или общие отчёты.

Отпечаток восстановленной схемы можно получить тем же read-only `archived-garages-plan` на отдельно восстановленной базе, с её точным `--expected-database` и новым private `--output`; использовать только `source.schemaFingerprint` этого результата. Он должен совпасть с source плана исходной базы. Host/имя/идентификатор проверочной базы не подставлять вместо source исходной базы в receipt.

## Применение

```sh
dotnet GarageBalance.StorageTool.dll archived-garages-cleanup \
  --execute \
  --plan /var/lib/garagebalance-staging/private-maintenance/archive-plan.json \
  --confirm EXACT_FINGERPRINT_FROM_PLAN \
  --backup-receipt /var/lib/garagebalance-staging/private-maintenance/verified-backup.json \
  --expected-database garagebalance_staging \
  --service garagebalance-staging.service \
  --reason "Очистка архивных гаражей без финансовой истории по согласованному заданию" \
  --output /var/lib/garagebalance-staging/private-maintenance/archive-result.json
```

Для установки без службы вместо `--service` можно указать `--application-port 3101` с настоящим портом остановленного backend. Требуется ровно один из этих вариантов, имя базы должно совпадать точно. Отпечаток не сокращать. Причина 3–500 символов обязательна. Новый отчёт не перезаписывает старый план или файл результата.

Операция блокирует выбранные гаражи, заново проверяет версии/связи после ожидания и выполняет удаление с аудитом в одной транзакции. Платёж, завершившийся во время ожидания FK-блокировки, виден повторной проверке и защищает гараж. Восстановленный гараж не удаляется. Любое изменение состава отменяет **всю** часть; надо создать новый предпросмотр, а не повторять старое подтверждение. При отправленном commit дочитывается его результат, даже если получен сигнал отмены.

В аудит записываются причина, ID/отпечаток плана, host administrator и SHA-256 проверенной копии; прежние события не удаляются. Если связь/финансовая история защищает запись, устранение этой защиты не входит в очистку. Финансовые записи не удалять ради получения подходящего плана.

При успехе сравнить `deletedGarages` с выбранным количеством и новый предпросмотр с исходным. Проверить сохранность исключённых гаражей/финансовых строк, владельцев и старого аудита, затем вернуть приложение в работу и проверить readiness. При обрыве связи или ошибке записи отчёта не считать, что удаление не произошло: проверить аудит и новый план. `cleanup_committed_report_failed` означает, что транзакция уже сохранена.

## Запуск на staging через GitHub Actions

Для staging не нужен ручной вход на узел: сценарий `Cleanup staging archived garages` (`.github/workflows/cleanup-staging-archived-garages.yml`) выполняет эти же команды через защищённую команду деплоя `garagebalance-deploy-apply archived-garages` и серверный скрипт `infrastructure/scripts/cleanup-staging-archived-garages.sh`.

1. Запустить сценарий с `operation: preview` и подтверждением `PREVIEW GARAGEBALANCE ARCHIVED GARAGES`. Данные не меняются. В журнале выводятся номера подходящих гаражей, количества причин защиты и отпечаток плана; сам план хранится в `/var/lib/garagebalance-staging/private-maintenance` с правами только для root.
2. Проверить перечень номеров вместе с заказчиком.
3. Не позднее чем через 23 часа запустить `operation: cleanup`, подтверждение `DELETE GARAGEBALANCE ARCHIVED GARAGES` и отпечаток из шага 1. Скрипт находит план по отпечатку, останавливает `garagebalance-staging.service`, делает `pg_dump`, восстанавливает его в отдельную временную базу, сверяет отпечаток схемы, формирует receipt, выполняет `archived-garages-cleanup --execute`, запускает службу, проверяет readiness и печатает итог нового предпросмотра. Временная база удаляется, а служба запускается и при ошибке.

Если состав изменился после предпросмотра, инструмент отменяет всю часть: нужен новый предпросмотр и новый отпечаток.

## Удаление архивного гаража вместе с финансовой историей

Команды `archived-garages-purge-plan` и `archived-garages-purge --execute` используются только по явному решению заказчика удалить тестовый гараж целиком (решение от 21.10.2026 по п. 4 замечаний). Они удаляют архивный гараж вместе с начислениями, оплатами, распределениями оплат, показаниями, приборами, подключениями, периодами численности, индивидуальными тарифами, участием в сборах и исправлениями начального остатка.

- Операции фондов, созданные оплатами гаража, исключаются из истории фонда. Цепочка `BalanceBefore/BalanceAfter` последующих операций и остаток фонда пересчитываются так же, как при отмене оплаты. Если остаток становится отрицательным, это отражается в аудите.
- Гараж не выбирается, если он входит в область действия услуги, на его оплаты ссылаются начисления поставщикам или пакеты выплат, либо оплаты других гаражей направлены на его начисления. В плане он попадает в `blockedGarageNumbers`.
- В аудит записываются удаление каждого гаража (`dictionary.garage_purged_with_financial_history`: количества и сумма действующих поступлений) и изменение каждого фонда (`fund.operations_removed_with_archived_garage`: остаток до и после).
- План ограничен 20 гаражами. В отпечаток входят состав и суммы начислений, оплат, операций фондов, показаний и приборов, поэтому любое изменение после предпросмотра отменяет удаление.

## Очистка тестовых показаний

Команды `meter-history-plan` и `meter-history-cleanup --execute` очищают форму «Показания» после проверки замены счётчиков (п. 6, решение от 21.10.2026):

- удаляются все показания, включая отменённые, и все приборы, установленные заменой; предыдущий прибор снова становится действующим;
- сохраняются стартовые значения: начальные показания карточки гаража, подключения и границы «Начало учёта». Если у счётчика гаража нет ни одного такого источника, его самое раннее показание остаётся как старт (`keptStartReadingCount`);
- начисления, рассчитанные по показаниям, отменяются; исторические суммы без формулы (`version` 0) остаются. Оплаты не меняются и перераспределяются: деньги за отменённые начисления становятся переплатой этой услуги;
- в аудит записываются итог по каждому гаражу (`finance.meter_history_cleared`) и общий итог (`finance.meter_history_cleanup`).

Если заменённый прибор служит стартом подключения или после замены установлен прибор, который сам не является заменой, предпросмотр отказывает: такой случай разбирается отдельно.

## Запуск новых очисток на staging

Сценарий `Cleanup staging test records` (`.github/workflows/cleanup-staging-records.yml`) вызывает `garagebalance-deploy-apply records` и серверный скрипт `infrastructure/scripts/cleanup-staging-records.sh` с теми же шагами, что и очистка архивных гаражей: предпросмотр, затем остановка службы, `pg_dump`, проверка восстановления во временной базе, receipt, выполнение, запуск службы, проверка readiness и новый предпросмотр.

| `kind` | Подтверждение предпросмотра | Подтверждение очистки |
|---|---|---|
| `garage-history` | `PREVIEW GARAGEBALANCE DELETED GARAGE HISTORY` | `DELETE GARAGEBALANCE DELETED GARAGE HISTORY` |
| `meter-history` | `PREVIEW GARAGEBALANCE METER HISTORY` | `DELETE GARAGEBALANCE METER HISTORY` |

Сначала удалять гаражи (`garage-history`), затем очищать показания (`meter-history`). После обеих операций запустить `Audit staging database`. Общий сброс рабочих данных этими командами не выполняется.
