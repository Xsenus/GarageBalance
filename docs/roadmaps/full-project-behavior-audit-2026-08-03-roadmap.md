# Полный аудит логики и поведения GarageBalance — 03.08.2026

## Источники

- Запрос заказчика: пройти весь проект, объяснить назначение и фактическую работу каждого раздела, проверить каждую форму и каждую строку кода, выделить логичные и нелогичные решения и предложить исправления.
- Текущий исходный код `backend`, `frontend`, `infrastructure`, workflow GitHub Actions и Docker-конфигурация.
- Пользовательская, административная, техническая и эксплуатационная документация в `docs`.
- EF Core-модель, миграции PostgreSQL, индексы и репозитории запросов.
- Автоматические backend/frontend/integration/deployment-тесты и фактический рендеринг приложения.
- Завершённые roadmap используются только как исторический контекст и не считаются доказательством текущей корректности.

## Допущения и решения

- Аудит является аналитической задачей: найденные дефекты фиксируются в отчёте, но код не изменяется без отдельного поручения заказчика.
- «Каждая строка кода» проверяется сочетанием ручного модульного чтения и автоматических статических проверок; выводы привязываются к конкретным файлам, методам, формам и сценариям.
- Корректность подтверждается текущим кодом, тестами, схемой БД и фактическим поведением; записи старых roadmap сами по себе доказательством не являются.
- Все пользовательские роли, успешные сценарии, пустые состояния, ошибки, отмена, устаревшие ответы, права и адаптивность рассматриваются отдельно.
- Безопасность персональных и финансовых данных оценивается без копирования реальных данных в отчёт.
- Итоговые замечания ранжируются как критические, высокие, средние и низкие с указанием риска и предлагаемого решения.

## Определение готовности

- Все checkable-пункты выше подтверждены текущими исходниками, тестами, БД или фактическим UI.
- Для каждого пользовательского раздела описаны назначение, нормальный поток, ограничения, роли, ошибки и спорные места.
- Для каждого backend-модуля описаны границы ответственности, ключевые правила, запросы и риски.
- Все замечания имеют конкретное доказательство, влияние, приоритет и предлагаемое исправление.
- Не используются широкие утверждения «всё работает» без проверяемого покрытия.
- Временные процессы и артефакты аудита удалены.

## Открытые риски и вопросы

- Полный ручной обход зависит от доступности обезличенной локальной БД и тестовых учётных записей всех ролей.
- Некоторые интеграции (1С Fresh, принтер, внешнее хранилище backup) могут требовать реального внешнего окружения; отсутствие такого окружения будет явно отмечено как непроверенный риск.
- Визуальная оценка субъективна; замечания отделяются от объективных функциональных, доступностных и производительных дефектов.

Поэтому watchdog и deploy могут считать сервис здоровым при недоступной БД — пользователь увидит shell и зависающие/ошибающиеся разделы, а автоматический перезапуск не сработает. Нужны раздельные `/health/live` и `/health/ready`, где readiness выполняет короткий запрос к БД и проверяет обязательные runtime-зависимости; deploy и nginx должны ждать readiness.
- 03.08.2026 — заявленный лимит Access-файла `512 МБ` недостижим на реальном контуре: nginx принимает максимум `50m`, ASP.NET multipart не переопределён и остаётся с платформенным пределом, а общий frontend write-timeout обрывает любой upload через `60` секунд. Даже после подключения reader крупная база будет отклонена прокси/формой либо прервана на медленном канале. Лимит должен быть единым на UI, Kestrel/form options, nginx и очереди; для upload нужен отдельный длительный/возобновляемый поток без общего write-timeout.
- 03.08.2026 — optimistic concurrency реализована только для показаний счётчиков. Остальные редактируемые агрегаты (гаражи, поставщики, тарифы, услуги, пользователи, фонды и настройки) не передают версию/ETag: две открытые формы могут молча перезаписать изменения друг друга. Для справочной и особенно финансовой конфигурации нужен version token и ответ `409` с показом конфликта, а не last-write-wins.
- 03.08.2026 — фоновая автоматизация начислений не имеет распределённого lease/advisory-lock на запуск. Уникальные индексы защищают часть начислений от фактического дубля, но два процесса одновременно выполнят одинаковые тяжёлые выборки и один из них может получить конфликт БД/частичный повтор. Перед поддержкой второго экземпляра API или случайным двойным локальным запуском нужен месячный PostgreSQL-lock и один журнал результата.
- 03.08.2026 — deploy хорошо проверяет тесты, coverage, форматирование, privacy, migration SQL, архивы, nginx и HTTP после переключения, но rollback возвращает только бинарники/frontend: уже применённая миграция БД не откатывается. Новая версия должна соблюдать expand/contract-совместимость с предыдущим бинарником либо deploy должен иметь проверенный DB restore-план; это необходимо явно закрепить gate-тестом. Также workflow доверяет результату `ssh-keyscan` без закреплённого fingerprint и не запускает dependency-vulnerability audit, хотя локально `npm audit --omit=dev` и `dotnet list package --vulnerable --include-transitive` сейчас не нашли уязвимостей.

- 03.08.2026 — обнаружен оставшийся публичный, но не используемый текущим frontend механизм `form-states`. Состояние хранится глобально только по строковому `Scope`, без `UserId`/организации и без списка разрешённых scope: пользователь с `payments.write` может записать произвольный JSON до 1 МБ, а любой пользователь с `dictionaries.read` — прочитать его. Права не соответствуют сохранявшимся ранее областям тарифов/контрагентов/платежей, два пользователя перезаписывают одну запись, а payload попадает в audit целиком. Текущий production frontend сервис не вызывает вообще, поэтому это лишняя поверхность доступа и потенциальное межпользовательское раскрытие/инъекция состояния. Следует удалить endpoint/таблицу после проверки совместимости либо ввести владельца, allowlist схем, корректные permission-политики, optimistic concurrency и безопасный audit без полного payload.

Такие записи сразу участвуют в регулярных начислениях; это не просто тестовые данные интерфейса. Отдельный большой демонстрационный набор защищён PostgreSQL-флагом `garagebalance.demo_seed_enabled`, а первоначальный каталог — нет. Можно вставить историческую строку со значением выше следующего показания и получить противоречивую цепочку. Нужна симметричная проверка следующего значения, транзакционный пересчёт затронутой последовательности и regression-тесты вставки между двумя месяцами.
- 2026-08-03: управление пользователями корректно требует хотя бы одну роль, не позволяет последовательно отключить или разжаловать последнего активного администратора, требует причину отключения и пишет аудит без пароля. Однако проверка «последнего администратора» выполняется отдельным чтением перед сохранением без общей блокировки: два администратора при конкурентных запросах могут одновременно увидеть второго и оба отключиться/потерять роль. Нужна транзакционная блокировка или БД-инвариант и конкурентный PostgreSQL-тест.
- 2026-08-03: backend допускает несколько ролей на пользователя, а форма создания/редактирования позволяет выбрать ровно одну и при сохранении заменяет весь набор массивом из одного кода. Если множественные роли нужны продукту, UI сейчас без предупреждения уничтожает дополнительные роли; если не нужны, API и модель следует упростить и закрепить ограничением. Это требует явного продуктового решения.
- 2026-08-03: корректировка, вставка, отмена или восстановление старого показания не перестраивает последующие показания. В каждой строке хранятся `PreviousValue` и `Consumption`, но изменение предыдущего месяца лишь проверяет границу следующего `CurrentValue`; следующий `PreviousValue`, его расход и начисление остаются прежними. Вставка пропущенного месяца и отмена строки имеют ту же проблему. Это критичный риск финансовой неверности: цепочка счётчика и начисления могут расходиться. Нужен единый транзакционный алгоритм пересчёта всей затронутой последовательности и связанных неоплаченных начислений с явной стратегией для уже оплаченных.
- 2026-08-03: карточка гаража позволяет в любое время напрямую изменить `StartingBalance` и стартовые показания без специального режима, причины и проверки наличия финансовой/счётчиковой истории. Стартовый баланс участвует во всех текущих остатках, поэтому его редактирование задним числом переписывает финансовый результат вместо отдельной корректировки. Стартовые показания также влияют на первый расход. После начала операций эти поля должны блокироваться, а исправления оформляться отдельными аудируемыми корректировками.
- 2026-08-03: владельца разрешено архивировать при наличии действующих гаражей. Связь остаётся, но последующее редактирование такого гаража отклоняется, потому что сервис принимает только активного владельца. Следует либо запрещать архивирование владельца с активными гаражами, либо атомарно переводить/отвязывать связи по явно подтверждённому сценарию; текущее промежуточное состояние нелогично.
- 2026-08-03: аналогичная неполнота обнаружена в иерархии поставщиков. Группу можно архивировать при активных поставщиках, а поставщика — при активных контактах; дочерние записи остаются рабочими, но их последующее редактирование/восстановление упирается в архивного родителя. Для отделов сотрудников такая защита уже есть, поэтому правила справочников непоследовательны. Нужна общая политика зависимостей: запрет с понятным списком связанных записей либо подтверждённое каскадное архивирование.
- 2026-08-03: `StartingBalance` поставщика, как и стартовый баланс гаража, изменяется непосредственно после появления начислений и выплат. Это меняет текущий долг задним числом без отдельной корректирующей операции. После начала истории стартовое значение должно стать неизменяемым, а корректировка долга — иметь дату, причину, аудит и собственную финансовую запись.
- 2026-08-03: семантическое поле `Code` у видов поступлений и статей расхода не уникально и пользовательский справочник разрешает повторить системные коды (`water`, `electricity`, `salary` и другие). Между тем расчёты, отчёты, сроки, выбор тарифа и кассовая логика ветвятся именно по коду, а часть репозиториев берёт `FirstOrDefault`/`SingleOrDefault`. Дубликат способен дать неоднозначное поведение или исключение. Коды должны быть нормализованы и уникальны среди активных записей, системные значения — зарезервированы.
- 2026-08-03: активные виды поступлений, статьи расхода и тарифы можно архивировать, даже если на них ссылается действующая услуга. После архивации услуга визуально остаётся активной, но исчезает из отдельных выборок/автоначислений или не может быть отредактирована; архив тарифа, например, исключает услугу из автоматических счётчиковых начислений. Нужна проверка активных зависимостей либо единая атомарная деактивация всей связки.
- 2026-08-03: самостоятельное редактирование тарифа позволяет поменять `CalculationBase`, не синхронизируя связанные `ChargeServiceSetting.IsMetered`, единицу и пороговый флаг. Тем самым можно создать запрещённую самим backend при сохранении услуги комбинацию. Изменение способа расчёта должно идти только через агрегат «услуга + версия тарифа» с проверкой связей и последствий для будущих начислений.
