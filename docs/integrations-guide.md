# Интеграции GarageBalance

## Импорт Microsoft Access

Reader работает через `mdbtools` и на каждом dry-run действительно открывает загруженную рабочую копию, получает список пользовательских таблиц и исключает системные `MSys*`. Временная копия создаётся в случайном закрытом каталоге и удаляется независимо от результата. В Docker `mdbtools` входит в API-образ; VPS-установщик добавляет пакет автоматически. Для локального запуска без Docker установите `mdbtools` и при необходимости задайте путь через `AccessImportReader:ExecutablePath`.

Если reader недоступен, dry-run остаётся безопасным, но показывает предупреждение и выполняет только сигнатурный анализ. Фактическое применение нельзя считать проверенным до успешного чтения таблиц. Повторная загрузка определяется по SHA-256, а заявку на применение или rollback можно повторно проследить по журналу запуска и audit.

Импорт используется для переноса старой базы `.accdb`/`.mdb` без ручного повторного ввода.

Безопасный процесс:

1. создать backup PostgreSQL;
2. загрузить рабочую копию Access-файла;
3. выполнить dry-run;
4. проверить найденные сущности, предупреждения и ошибки;
5. разобрать quarantine;
6. подтвердить применение импорта;
7. сверить количества, суммы и показания;
8. сохранить технический отчёт без исходных персональных данных.

После загрузки файл сохраняется под случайным идентификатором в закрытой очереди, а HTTP-запрос сразу возвращает наблюдаемый запуск со статусом `queued`. Worker потоково рассчитывает SHA-256, держит в памяти не более 4 МБ образца и удаляет временный файл после результата. Незавершённый запуск и его файл восстанавливаются после перезапуска. В Docker очередь хранится в `IMPORT_QUEUE_HOST_PATH`; каталог обязательно остаётся вне Git.

Повторный импорт защищён fingerprints строк; проверка существующих ключей и запись новых fingerprints выполняются пакетами до 1000 строк. Фактическое применение и rollback выполняются как наблюдаемые операции и фиксируются в audit. Raw-файлы и снимки строк не публикуются в Git и не возвращаются обычным API.

## 1C Fresh

Интеграция строится как backend-синхронизация: токены хранятся через ASP.NET Core Data Protection, браузер не получает plaintext. Перед фактическим обменом выполняется preview, после чего пользователь подтверждает операцию.

Запуск и ручной повтор помещаются в ограниченную фоновую очередь. Внешний адаптер выполняется в отдельном scope без открытой DB-транзакции и ограничен тайм-аутом; медленный внешний сервис не удерживает HTTP-запрос пользователя. Записи не повторяются автоматически: после временной ошибки интерфейс явно предлагает безопасный ручной повтор.

Рабочий транспорт реализован через совместимый HTTP-шлюз. Для включения задайте `Integrations__OneCFreshAdapter__Enabled=true` и `Integrations__OneCFreshAdapter__Endpoint=https://...`. Endpoint обязан использовать HTTPS; обычный HTTP допускается только для локального шлюза. GarageBalance отправляет `POST` с Bearer-токеном из защищённого хранилища и JSON-полями `comment`, `requestedAtUtc`, `isRetry`. Шлюз отвечает JSON-полями `statusMessage`, `externalRunId`, `errorCode`; `409` считается бизнес-конфликтом, остальные ошибки можно безопасно повторить вручную. Токен не возвращается клиенту и не записывается в диагностические сообщения.

Пока адаптер выключен или endpoint некорректен, статус честно показывает недоступность, предпросмотр не разрешает запуск и никакие внешние данные не отправляются. После включения предпросмотр разрешает подтверждение и поясняет, что состав документов и период определяет настроенный шлюз.

Синхронизация должна быть идемпотентной, иметь внешний идентификатор, журнал запуска, повтор после временной ошибки и понятную сверку созданных/обновлённых/пропущенных записей.

Набор передаваемых данных и рабочий контур согласуются отдельно до включения production-синхронизации.

## Печать квитанций и чеков

Печать отделена от финансовой операции: сначала backend сохраняет и подтверждает платёж, затем создаётся задание печати. Ошибка устройства не должна создавать второй платёж.

Действие `Полная оплата` присваивает всем созданным строкам одного гаража и одной даты общий идентификатор пакета. При печати backend собирает действующие поступления пакета, их виды услуг и активные распределения по начислениям, вычисляет единый итог и передаёт адаптеру одно задание с позициями. Обычное одиночное поступление без пакета сохраняет прежний сценарий одной квитанции. Пакет с выплатой, другим гаражом или другой датой отклоняется; один документ ограничен 100 финансовыми позициями.

Шаблон документа получает только необходимые реквизиты. Секреты оборудования и интеграционные адреса хранятся как защищённые настройки. Каждая попытка печати имеет статус и запись в истории.

Рабочий транспорт печати также использует HTTP-шлюз. Для включения задайте `Integrations__ReceiptPrintingAdapter__Enabled=true` и `Integrations__ReceiptPrintingAdapter__Endpoint=https://...`; HTTP допустим только для локального адреса. Перед каждым заданием backend читает `ReceiptPrinting:DeviceConnection` и `ReceiptPrinting:ReceiptTemplate` из защищённого хранилища и передаёт их шлюзу вместе с полным заданием `job`. Успешный ответ может вернуть `statusMessage`, `deviceResponseCode` и `externalReceiptId`. При отсутствии любой защищённой настройки, тайм-ауте или отказе шлюза платёж не создаётся повторно, а попытка остаётся доступной для контролируемого повтора.

Перед включением production endpoint необходимо подтвердить модель устройства, обязательные реквизиты, формат документа и юридические требования; сам адаптер и его отказоустойчивые ветви проверяются без раскрытия этих данных.
