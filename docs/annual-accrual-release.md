# Проверка и возобновление годовых начислений

## Назначение и границы

Приостановка относится к отдельно выбранному году. Обновление программы само по себе её не снимает. Перед возобновлением администратор проверяет финансовый эффект, резервную копию и установленную защиту обслуживания. Не менять `finance.annual_accrual_hold.*` вручную SQL-запросом.

Команды выполняются администратором на разрешённом узле с существующей конфигурацией приложения. Не передавать пароли, токены, connection strings или дампы в переписке. Не создавать новые роли или постоянный доступ ради запуска. Пользователь с доступом к интерфейсу может проверить настройку периода и историю начислений, но это не заменяет серверную квалификацию.

## Безопасный финансовый прогноз

```sh
dotnet GarageBalance.StorageTool.dll annual-accrual-impact-plan \
  --annual-hold-year 2026 \
  --expected-database garagebalance_staging \
  --output /var/lib/garagebalance-staging/private-maintenance/annual-impact-2026.json
```

Выходной файл должен быть новым, абсолютным и private. Существующий файл не перезаписывается. Прогноз использует согласованный read-only снимок PostgreSQL, действительную бизнес-дату и часовой пояс, начало учёта, годовые услуги, тарифные условия и актуальные ручные отмены. Он не вызывает генерацию начислений и не записывает настройки, финансовые строки или аудит.

Суммы относятся к пропущенным регулярным годовым взносам текущего бизнес-года с наступившим сроком по текущий бизнес-месяц. Новые суммы означают начисления, а не итоговую задолженность после оплат, зачётов и начальных остатков. Это не оценка всех будущих платежей года: после снятия приостановки будущие сроки будут обрабатываться штатно по действующим тогда условиям.

В отчёте находятся только источник, технические идентификаторы услуг и агрегаты: подходящие гаражи, уже созданные обязательства, новые суммы, исключения и неопределённые случаи. Нет номеров гаражей, владельцев, контактов или комментариев. `inputFingerprint` связывает точные входы; `fingerprint` связывает сам отчёт. Одинаковые суммы при разных входах не означают одинаковый план.

`isComplete=false` и exit code 3 означают, что точного разрешения на возобновление нет. Суммы поддержанной части нельзя выдавать за итог всей организации. Например, неподдержанные годовые сборы, неоднозначная классификация или тарифный сценарий требуют отдельной проверки. Exit code 0 означает успешно построенный полный прогноз, но не снятую приостановку и не разрешение выполнить SQL.

Обычная вкладка годовых платежей при действующей приостановке показывает существующие обязательства и может скрывать будущие строки. Её нулевой итог не является прогнозом снятия приостановки.

## Подтверждаемый план

```sh
dotnet GarageBalance.StorageTool.dll annual-accrual-release-plan \
  --annual-hold-year 2026 \
  --expected-database garagebalance_staging \
  --output /var/lib/garagebalance-staging/private-maintenance/annual-release-2026.json
```

План связывает год, точный источник и схему, содержимое и версии настройки/guard epoch, полный финансовый прогноз, ID операции и fingerprint. Старые планы без нового формата и полного прогноза не годятся. Проверить суммы и охват отдельно; не считать техническую генерацию плана бизнес-подтверждением.

После плана нужна свежая согласованная резервная копия и фактическое успешное восстановление в отдельную проверочную базу. Receipt описан в [руководстве maintenance](accounting-cleanup-cli.md#проверенная-резервная-копия). Копия должна быть не раньше плана, не старше разрешённого окна и соответствовать точному источнику/схеме. Нельзя ставить `restoreSucceeded=true` только потому, что dump существует.

## Защищённое исполнение

```sh
dotnet GarageBalance.StorageTool.dll annual-accrual-release \
  --execute \
  --plan /var/lib/garagebalance-staging/private-maintenance/annual-release-2026.json \
  --confirm EXACT_FINGERPRINT_FROM_APPROVED_PLAN \
  --backup-receipt /var/lib/garagebalance-staging/private-maintenance/verified-backup.json \
  --expected-database garagebalance_staging \
  --service garagebalance-staging.service \
  --reason "Возобновление годовых начислений по проверенным суммам и охвату"
```

Исполнение требует квалифицированных установленных entrypoints, root-owned файлов и точного staging target. Под эксклюзивным deploy gate создаётся устойчивый marker, затем приложение и фоновые участники останавливаются и дренируются; после этого приобретается эксклюзивный activity gate. Закрытый permit привязан к этой операции; его нельзя заменить параметром, переменной окружения или подставной проверкой.

Перед commit повторно проверяются прогнозные входы, политика, backup receipt, locks и остановка приложения. Изменение входов, неполный прогноз, посторонний клиент, потеря lock или сомнительный исход прекращают операцию. SQL-транзакция меняет только согласованный hold, epoch и пишет аудит. Сама SQL-операция release не создаёт начисления. После доказанного commit восстанавливается прежнее состояние участников; включённый фоновый расчёт может сформировать согласованные начисления уже при запуске приложения, до завершения команды. Поэтому ноль `generatedByRelease` не означает, что после возобновления приложения вообще не появятся финансовые строки.

Не запускать release повторно при потере связи, timeout, сигнале отмены или неизвестном результате.

## Восстановление после прерывания

```sh
dotnet GarageBalance.StorageTool.dll annual-accrual-release-recover \
  --execute \
  --plan /var/lib/garagebalance-staging/private-maintenance/annual-release-2026.json \
  --confirm EXACT_FINGERPRINT_FROM_APPROVED_PLAN \
  --expected-database garagebalance_staging \
  --service garagebalance-staging.service
```

Используется тот же точный план. Recovery читает настройку, epoch и аудит и доказывает committed либо rolled-back. Оно не вызывает release второй раз. При неизвестном исходе marker остаётся и приложение не возобновляется. Не удалять marker/receipt вручную, не сбрасывать службу ради обхода защиты.

Гарантия относится к штатным фазам протокола, частичным записям и неопределённому commit. Произвольная внешняя порча уже синхронизированного root-owned receipt после снятия marker не равна этим сценариям: существующий app-wrapper не читает закрытые bytes receipt до запуска. При таком вмешательстве требуется остановка и отдельное расследование; этот этап не меняет права wrapper и не заявляет защиту от администратора узла.

## Проверка результата

Сверить точный год и один audit результата, сохранность остальных лет, финансовых/справочных строк и ожидаемое состояние участников. Затем сравнить штатные начисления с согласованным прогнозом, проверить отсутствие дублей и сохранение ручных отмен.

Для прежних жалоб гаражей 1 и 13 начать с «Истории изменений»: последний lifecycle event по начислению, флаг отмены, услуга, месяц/год и сумма. Старое событие отмены без проверки последующего восстановления недостаточно. Открытие формы «Поступления» не является строго read-only действием: worksheet может создавать/нормализовать начисления сборов.

Начальный период: «Настройки → Отображение → Начальный период поступлений → При открытии гаража показывать месяцы с первого долга». Сохранённый ранее false сохраняется до явного изменения и кнопки «Сохранить отображение».

## Доказательства и пределы проверки

Синтетические PostgreSQL тесты проверяют snapshot, drift, rollback, отсутствие изменений финансов и равенство поддержанного прогноза штатному расчёту. Изолированный Linux/systemd fixture проверяет crash/recovery, конкурентные запуски и cleanup. Windows build или `bash -n` не заменяют его исполнения. Зелёный CI fixture не квалифицирует установленный VPS: реальные пути, хеши, ownership, units/drop-ins/triggers и backup/restore проверяются отдельно.
