# Отказоустойчивое хранение резервных копий

## Назначение и границы

GarageBalance сохраняет PostgreSQL backup сначала в локальное горячее хранилище, проверяет размер и SHA-256 и только затем регистрирует логический объект. В режиме `AsyncMirror` фоновые задания доставляют ту же неизменяемую генерацию в разрешённые назначения. Успех локального `pg_dump` и состояние защиты независимы: копия может быть создана, но ещё ожидать требуемое число независимых реплик.

Система не имитирует успех, если нет ни одной проверенной копии. Отказ одного назначения не делает приложение глобально неготовым и не останавливает задания для других назначений. Возвратившееся хранилище не становится источником истины по имени: его объект сверяется по поколению, размеру и SHA-256 и при необходимости восстанавливается из актуальной проверенной копии.

## Режимы

- `Single` — совместимый режим по умолчанию. Используется локальный каталог из `DatabaseBackup__Directory`; новые облачные параметры не требуются.
- `AsyncMirror` — локальная проверенная копия плюс асинхронные независимые реплики. Объект считается защищённым только при выполнении `RequiredIndependentCopies` с разными `FailureDomain` и фактическом наличии `MinimumOffsiteCopies` внешних копий. Две папки одного компьютера не являются независимой внешней защитой.

Секреты S3 не записываются в JSON проекта. Адаптер использует стандартную цепочку учётных данных SDK (`DefaultChain`/workload identity). Endpoint должен быть HTTPS, кроме явно разрешённого изолированного локального тестового стенда.

## Подключение Cloud.ru Evolution Object Storage

Бакет `sgk-garagebalance` — одно внешнее назначение, а не самостоятельная настроенная система backup. Для Cloud.ru Evolution используются S3 endpoint `https://s3.cloud.ru`, регион подписи `ru-central-1` и path-style адресация. ID бакета из личного кабинета не является S3-ключом: в конфигурации нужен именно **название** бакета. Публичный доступ, хостинг сайта и общий доступ к объектам для резервных копий не включать.

1. В Cloud.ru создайте **сервисный аккаунт уровня проекта**, ограниченный этим проектом, и назначьте ему роли `s3e.viewer` и `s3e.editor` **только на бакет** `sgk-garagebalance`. `s3e.admin` и общая роль администратора проекта не нужны. Создайте для аккаунта ключ доступа с ограниченным сроком действия. Для S3 `AWS_ACCESS_KEY_ID` имеет формат `<tenant_id>:<key_id>`, `AWS_SECRET_ACCESS_KEY` — выданный `Key Secret`. `tenant_id` находится в Object Storage → «Параметры работы с API». Это не ID бакета. Секрет не передавайте в чат, не помещайте в репозиторий или общий `.env`; храните в защищённом хранилище секретов рабочего хоста. Убедитесь, что у владельца есть процедура ротации и восстановления ключа.
2. Пока отдельного ключа сервисного аккаунта и полной проверки восстановления нет, приложение оставьте в `Storage:Mode=Single`. Реальный тест 23.09.2026 подтвердил, что Cloud.ru отклоняет применявшийся ранее заголовок SSE-S3 `AES256`. Для этого назначения используйте `EncryptionMode=SseKms`: создан симметричный ключ Cloud.ru Key Management; предоставьте будущему сервисному аккаунту право `sckm.user`, укажите ID ключа в `KmsKeyId`. Не удаляйте и не деактивируйте KMS-ключ, пока существуют зашифрованные им резервные копии. Ключ KMS — отдельная зависимость аварийного восстановления; заранее проверьте доступ к нему с нового хоста.
3. Локальная проба 23.09.2026 с временным персональным доступом проверила `PutObject`, `HeadObject`, `GetObject`, SHA-256, `DeleteObject` и multipart SSE-KMS на отдельных объектах, включая отсутствие объектов после удаления. В первом multipart-прогоне был выявлен и исправлен пропуск SHA-256 частей в запросе завершения; повторный прогон прошёл. Это подтверждает совместимость операций, но не права будущего сервисного аккаунта, доставку настоящих дампов, восстановление на другом хосте или скорость на рабочем объёме. Перед включением повторите проверку с отдельным сервисным аккаунтом и дампом подходящего размера; опубликованный в чате персональный ключ отзовите после временных проб.
4. После успешного теста зафиксируйте постоянный `Id`, `FailureDomain` и префикс. Пример **неактивной заготовки** `Storage` для Linux/Docker приведён ниже. Локальный путь замените на каталог реальных backup соответствующей установки, а `TenantId` — на постоянный идентификатор этой установки. Секретных полей в JSON нет. Настройку помещайте только в закрытую конфигурацию конкретного хоста, не в общий `appsettings.json`.

```json
{
  "Storage": {
    "Mode": "Single",
    "TenantId": "garagebalance",
    "Destinations": [
      {
        "Id": "local-hot",
        "Type": "LocalFileSystem",
        "State": "Enabled",
        "FailureDomain": "local-host",
        "TenantId": "garagebalance",
        "RootPath": "/backups",
        "Capabilities": ["Read", "Write", "Stat", "Delete"]
      },
      {
        "Id": "cloudru-cold",
        "Type": "S3Compatible",
        "State": "Enabled",
        "FailureDomain": "cloudru-evolution-moscow",
        "TenantId": "garagebalance",
        "Endpoint": "https://s3.cloud.ru",
        "AllowedEndpointHosts": ["s3.cloud.ru"],
        "Bucket": "sgk-garagebalance",
        "Prefix": "garagebalance/backups",
        "SigningRegion": "ru-central-1",
        "ForcePathStyle": true,
        "CredentialSource": "DefaultChain",
        "EncryptionMode": "SseKms",
        "KmsKeyId": "REPLACE_WITH_CLOUDRU_KMS_KEY_ID",
        "PrivateAccess": true,
        "EncryptionAtRest": true,
        "Capabilities": ["Read", "Write", "Stat", "Delete", "ServerSideEncryption"]
      }
    ],
    "Pools": [{ "Id": "database-backups", "DestinationIds": ["local-hot", "cloudru-cold"] }],
    "Policies": [{
      "Id": "database-backups",
      "DataClass": "DatabaseBackup",
      "PoolId": "database-backups",
      "RequiredIndependentCopies": 2,
      "MinimumOffsiteCopies": 1,
      "DesiredCopies": 2
    }]
  }
}
```

Заготовка намеренно сохраняет `Mode=Single`: само её внесение не включает облачную доставку. Только после реального теста провайдера, проверки отдельной копии ключей Data Protection, контрольного восстановления, планирования расходов и наблюдения за защитой смените режим на `AsyncMirror` в закрытой конфигурации хоста. Для уже существующих дампов потребуется `inventory`/`plan`/`copy`/`verify`/`cutover-check`, а не только переключение режима. Холодный класс Cloud.ru рассчитан на редкие обращения: чтение/запись обходятся дороже стандартного, и маленькие объекты тарифицируются минимум как 128 КБ; оцените стоимость регулярной проверки и восстановления перед включением. Один бакет Cloud.ru даёт одну внешнюю площадку для политики «локальная + внешняя»; для полного плана с двумя независимыми внешними назначениями всё ещё нужен другой провайдер/домен отказа.

`Id` и `FailureDomain` описывают идентичность назначения и не должны переименовываться для уже записанных копий. При смене площадки создайте новое назначение и выполните проверяемую доставку. Копия с несовпадающим сохранённым доменом, вне текущего пула или без возможностей чтения/проверки не считается пригодной защитой; изменение названия само по себе не доказывает перенос данных.

### Подключение staging-VPS

Релиз поставляет на VPS отдельный операторский инструмент и ограниченную команду `garagebalance-deploy-apply cloud-backup`. Она не принимает секреты в аргументах или логах: при первичном включении Key ID и Key Secret подаются двумя строками через стандартный ввод. Скрипт создаёт `/etc/garagebalance-staging-cloud.env` с правами `0600` и systemd drop-in, затем перезапускает API. Если сервис или `/health/ready` не запустится, новая настройка снимается и прежний режим восстанавливается. Повторное применение поверх существующей настройки запрещено: смену ключа проводите отдельной контролируемой ротацией, не удаляя предыдущие копии.

После запуска выполнить инвентаризацию и перенос **всех** локальных `.pgdump`, включая предрелизные и исторические архивы: `cloud-backup inspect`, затем `cloud-backup run inventory`, `plan`, `copy`, `verify`, `cutover-check`. Неизвестный формат имени не пропускается молча, а блокирует приёмку. Команда `copy` сохраняет закрытую контрольную точку в `/var/lib/garagebalance-staging/storage-migration`; при прерывании используйте `resume`, а для новых файлов — `delta-sync`. Команды не удаляют источники. После положительного `cutover-check` включить `cloud-backup schedule`: systemd ежечасно запускает `delta-sync` для архивов, добавленных вне приложения, в том числе предрелизных. Пока облачная конфигурация активна, deploy-скрипт не удаляет локальные предрелизные архивы за пределами каталога. Не считать включённый режим доказательством существования облачных копий до положительного результата `cutover-check`.

Персональный ключ, опубликованный в чате и временно разрешённый владельцем для запуска, после проверки нужно заменить ограниченным ключом сервисного аккаунта и отозвать старый. Не ослабляйте закрытость бакета и SSE-KMS. Ключи ASP.NET Data Protection и конфигурация восстановления требуют отдельного зашифрованного recovery bundle: выгрузка одних `.pgdump` ещё не означает полный DR при потере VPS.

## Состояния в интерфейсе

- **Защищена** — политика независимых проверенных копий выполнена.
- **Ожидает копирования** — локальный backup готов, доставка выполняется в фоне.
- **Защита ослаблена** — пригодная копия есть, но независимых копий меньше нормы.
- **Требует внимания** — нет достаточной проверенной копии или исчерпан безопасный повтор.
- **Удаляется** — логический tombstone уже запрещает чтение, физические копии удаляются отдельными заданиями.

Право `backups.repair` разрешает действия «Проверить защиту» и «Повторить защиту». Backend проверяет право независимо от интерфейса, а действие записывается в аудит без путей, bucket и реквизитов доступа.

Статус раскрывается клавиатурой или мышью: видны доступное/необходимое/целевое количество копий, внешние копии, задержка доставки, последнее подтверждение и безопасная причина ошибки каждого назначения. Проверка SHA и пробное восстановление — разные проверки. Отдельная строка показывает результат и возраст последнего пробного восстановления; отсутствие настроенного проверяющего задания не считается успехом.

Проверка каталога использует полный постраничный обход, а не только первые 100 объектов. При массовых аномалиях автоматический ремонт приостанавливается до явного решения оператора; пауза сохраняется после перезапуска. Повреждённые исходники сохраняются в карантине для расследования и учитываются в ограничении локального места. Автоматическое удаление старой защищённой копии ждёт защищённую замену в сохраняемом окне.

## Инвентаризация и перенос

Операторский инструмент по умолчанию только читает состояние. Команды, способные создать задания или копии, требуют явного `--execute`; команды удаления источника отсутствуют.

```powershell
dotnet run --project backend/GarageBalance.StorageTool -- inventory
dotnet run --project backend/GarageBalance.StorageTool -- plan --output C:\GarageBalance\Reports\storage-plan.json
dotnet run --project backend/GarageBalance.StorageTool -- copy --execute --max-jobs 100 --checkpoint C:\GarageBalance\Reports\storage-migration.json
dotnet run --project backend/GarageBalance.StorageTool -- verify --execute
dotnet run --project backend/GarageBalance.StorageTool -- delta-sync --execute --checkpoint C:\GarageBalance\Reports\storage-migration.json
dotnet run --project backend/GarageBalance.StorageTool -- cutover-check
dotnet run --project backend/GarageBalance.StorageTool -- rollback-check
```

Порядок миграции: `inventory` → `plan` → `copy` → `verify` → повторный `delta-sync` → `cutover-check`. Задания находятся в PostgreSQL, а проверяемый checkpoint — в атомарном независимом файле. `resume` продолжает именно сохранённый план; `delta-sync` добавляет новые файлы и изменения. Миграция не выполняет задания удаления. Проверки переключения читают реальные байты всех сохраняемых архивов; откат дополнительно требует локальную копию. Полные параметры, ограничения, причины ненулевого кода и снятие карантина: [инструмент миграции](storage-migration-cli.md). Восстановление без исходной БД и ключевого каталога: [аварийное восстановление](disaster-recovery.md).

## Инцидент и возврат назначения

1. Проверить статус копий и структурные логи `Storage protection is incomplete/failed`.
2. Не снижать `RequiredIndependentCopies` для сокрытия проблемы.
3. Устранить сеть, квоту, права или TLS. Не отключать проверку сертификата.
4. Нажать «Проверить защиту» или выполнить `verify --execute`; при необходимости — «Повторить защиту»/`repair --execute`.
5. Дождаться статуса «Защищена» и нулевого долга до возврата назначения в приоритет.

Circuit breaker ведётся отдельно для чтения, записи, удаления и проверки. `404` одного объекта не отключает всё назначение; ошибки credentials/forbidden/quota/TLS открывают соответствующий операционный контур немедленно, сетевые ошибки — после ограниченного числа попыток. Полуоткрытая проверка допускает только один пробный запрос после cooldown.

## Проверяемое восстановление

Структуру и SHA backup нужно проверять до восстановления. Восстановление выполняется только в отдельную базу; защищённые имена блокируются без отдельного опасного флага.

```powershell
.\infrastructure\scripts\restore-postgres.ps1 `
  -BackupFile C:\GarageBalance\Backups\garagebalance_manual_20260922_120000_000.pgdump `
  -TargetDatabase garagebalance_restore_check `
  -DropAndCreate `
  -VerifyAndDrop
```

Скрипт проверяет sidecar-манифест, SHA-256, TOC `pg_restore`, выполняет restore с `--exit-on-error`, проверяет наличие прикладных таблиц и `__EFMigrationsHistory`, измеряет длительность и при `-VerifyAndDrop` всегда удаляет одноразовую базу.

## Recovery bundle

Ключи ASP.NET Data Protection нужны для расшифровки уже защищённых настроек после потери хоста. Они упаковываются отдельно от database backup и шифруются AES-256-GCM ключом, который хранится в другом контуре.

```powershell
.\infrastructure\scripts\recovery-bundle.ps1 -Mode Protect `
  -EncryptionKeyFile E:\OfflineKeys\garagebalance-recovery.key `
  -KeyRingDirectory C:\GarageBalance\Keys `
  -NonSecretConfigFiles C:\GarageBalance\appsettings.Production.json `
  -BundleFile C:\GarageBalance\Backups\garagebalance-recovery.gbrecovery
```

`.env`, private keys, certificates и password-файлы нельзя включать. Ключ шифрования нельзя хранить рядом с bundle. Распаковка выполняется в новый ACL-защищённый каталог командой `-Mode Unprotect`; существующий каталог не перезаписывается.

## Подключение и откат

Безопасная последовательность: применить additive-миграцию → оставить `Single` → настроить назначения → включить `AsyncMirror` для новых backup → выполнить backfill → подтвердить `cutover-check` → включить эксплуатацию fallback. Не включать provider lifecycle/Object Lock без отдельного решения владельца.

Откат: прекратить новые задания, сохранить каталог и все физические копии, выполнить `rollback-check`. Возврат к `Single` допустим только после того, как все актуальные B-only объекты снова доступны локально. Схема каталога additive и не требует удаления данных при откате бинарной версии.

## Внешние критерии приёмки

До production-включения владелец/оператор должен предоставить два действительно независимых назначения, утвердить RPO/RTO/retention, канал уведомлений и разрешить изолированный DR drill. Требуются реальные проверки ошибок выбранного провайдера, восстановление из независимой копии вместе с recovery bundle и зафиксированные фактические RPO/RTO. Локальные эмуляторы и unit-тесты не заменяют эту приёмку.
