# Отказоустойчивое хранение резервных копий

## Назначение и границы

GarageBalance сохраняет PostgreSQL backup сначала в локальное горячее хранилище, проверяет размер и SHA-256 и только затем регистрирует логический объект. В режиме `AsyncMirror` фоновые задания доставляют ту же неизменяемую генерацию в разрешённые назначения. Успех локального `pg_dump` и состояние защиты независимы: копия может быть создана, но ещё ожидать требуемое число независимых реплик.

Система не имитирует успех, если нет ни одной проверенной копии. Отказ одного назначения не делает приложение глобально неготовым и не останавливает задания для других назначений. Возвратившееся хранилище не становится источником истины по имени: его объект сверяется по поколению, размеру и SHA-256 и при необходимости восстанавливается из актуальной проверенной копии.

## Режимы

- `Single` — совместимый режим по умолчанию. Используется локальный каталог из `DatabaseBackup__Directory`; новые облачные параметры не требуются.
- `AsyncMirror` — локальная проверенная копия плюс асинхронные независимые реплики. Объект считается защищённым только при выполнении `RequiredIndependentCopies` с разными `FailureDomain`.

Секреты S3 не записываются в JSON проекта. Адаптер использует стандартную цепочку учётных данных SDK (`DefaultChain`/workload identity). Endpoint должен быть HTTPS, кроме явно разрешённого изолированного локального тестового стенда.

## Состояния в интерфейсе

- **Защищена** — политика независимых проверенных копий выполнена.
- **Ожидает копирования** — локальный backup готов, доставка выполняется в фоне.
- **Защита ослаблена** — пригодная копия есть, но независимых копий меньше нормы.
- **Требует внимания** — нет достаточной проверенной копии или исчерпан безопасный повтор.
- **Удаляется** — логический tombstone уже запрещает чтение, физические копии удаляются отдельными заданиями.

Право `backups.repair` разрешает действия «Проверить защиту» и «Повторить защиту». Backend проверяет право независимо от интерфейса, а действие записывается в аудит без путей, bucket и реквизитов доступа.

## Инвентаризация и перенос

Операторский инструмент по умолчанию только читает состояние. Команды, способные создать задания или копии, требуют явного `--execute`; команды удаления источника отсутствуют.

```powershell
dotnet run --project backend/GarageBalance.StorageTool -- inventory
dotnet run --project backend/GarageBalance.StorageTool -- plan --output C:\GarageBalance\Reports\storage-plan.json
dotnet run --project backend/GarageBalance.StorageTool -- copy --execute --max-jobs 100
dotnet run --project backend/GarageBalance.StorageTool -- verify --execute
dotnet run --project backend/GarageBalance.StorageTool -- delta-sync --execute
dotnet run --project backend/GarageBalance.StorageTool -- cutover-check
dotnet run --project backend/GarageBalance.StorageTool -- rollback-check
```

Порядок миграции: `inventory` → `plan` → `copy` → `verify` → повторный `delta-sync` → `cutover-check`. Остановка безопасна: задания и курсор находятся в PostgreSQL, локальный источник не удаляется, повтор команды идемпотентен. Код возврата `10` у `cutover-check`/`rollback-check` означает, что не все retained-объекты имеют требуемое число независимых копий.

## Инцидент и возврат назначения

1. Проверить статус копий и структурные логи `Storage protection is incomplete/failed`.
2. Не снижать `RequiredIndependentCopies` для сокрытия проблемы.
3. Устранить сеть, квоту, права или TLS. Не отключать проверку сертификата.
4. Нажать «Проверить защиту» или выполнить `verify --execute`; при необходимости — «Повторить защиту»/`repair --execute`.
5. Дождаться статуса «Защищена» и нулевого долга до возврата назначения в приоритет.

Circuit breaker ведётся отдельно для чтения, записи, удаления и проверки. `404` одного объекта не отключает всё назначение; ошибки credentials/forbidden/quota/TLS открывают соответствующий операционный контур немедленно, сетевые ошибки — после ограниченного числа попыток. Полуоткрытая проверка допускает только один пробный запрос после cooldown.

## Проверяемое восстановление

Структуру и SHA backup нужно проверять до восстановления. Восстановление выполняется только в отдельную базу; защищённые имена блокируются без отдельного опасного флага.

```powershell
.\infrastructure\scripts\restore-postgres.ps1 `
  -BackupFile C:\GarageBalance\Backups\garagebalance_manual_20260922_120000_000.pgdump `
  -TargetDatabase garagebalance_restore_check `
  -DropAndCreate `
  -VerifyAndDrop
```

Скрипт проверяет sidecar-манифест, SHA-256, TOC `pg_restore`, выполняет restore с `--exit-on-error`, проверяет наличие прикладных таблиц и `__EFMigrationsHistory`, измеряет длительность и при `-VerifyAndDrop` всегда удаляет одноразовую базу.

## Recovery bundle

Ключи ASP.NET Data Protection нужны для расшифровки уже защищённых настроек после потери хоста. Они упаковываются отдельно от database backup и шифруются AES-256-GCM ключом, который хранится в другом контуре.

```powershell
.\infrastructure\scripts\recovery-bundle.ps1 -Mode Protect `
  -EncryptionKeyFile E:\OfflineKeys\garagebalance-recovery.key `
  -KeyRingDirectory C:\GarageBalance\Keys `
  -NonSecretConfigFiles C:\GarageBalance\appsettings.Production.json `
  -BundleFile C:\GarageBalance\Backups\garagebalance-recovery.gbrecovery
```

`.env`, private keys, certificates и password-файлы нельзя включать. Ключ шифрования нельзя хранить рядом с bundle. Распаковка выполняется в новый ACL-защищённый каталог командой `-Mode Unprotect`; существующий каталог не перезаписывается.

## Подключение и откат

Безопасная последовательность: применить additive-миграцию → оставить `Single` → настроить назначения → включить `AsyncMirror` для новых backup → выполнить backfill → подтвердить `cutover-check` → включить эксплуатацию fallback. Не включать provider lifecycle/Object Lock без отдельного решения владельца.

Откат: прекратить новые задания, сохранить каталог и все физические копии, выполнить `rollback-check`. Возврат к `Single` допустим только после того, как все актуальные B-only объекты снова доступны локально. Схема каталога additive и не требует удаления данных при откате бинарной версии.

## Внешние критерии приёмки

До production-включения владелец/оператор должен предоставить два действительно независимых назначения, утвердить RPO/RTO/retention, канал уведомлений и разрешить изолированный DR drill. Требуются реальные проверки ошибок выбранного провайдера, восстановление из независимой копии вместе с recovery bundle и зафиксированные фактические RPO/RTO. Локальные эмуляторы и unit-тесты не заменяют эту приёмку.
